# MeetingOps — Implementation Decisions

Phase 0 artifact. Each decision records: the ambiguity/conflict found, the resolution, and why. Rule applied: smallest coherent implementation that preserves the golden scenario and WebMCP requirements. No decision weakens a security, approval, or verification constraint.

| # | Decision | Rationale |
| --- | --- | --- |
| D-001 | **Doc numbering.** The implementation prompt references `03_WEBMCP_SPEC`, `04_DOMAIN_DATA_API`, … while the repo ships `02_WEBMCP_SPEC.md`, `03_DOMAIN_DATA_API.md`, … (one-index offset). | README.md fixes the canonical file list; content maps 1:1 by title. Repo numbering used throughout; no content conflict exists. |
| D-002 | **Traceability filename.** `01_BUILD_INSTRUCTIONS` says `docs/IMPLEMENTATION_TRACEABILITY.md`; the harness prompt says `docs/requirements-traceability.md`. | One canonical file: `docs/requirements-traceability.md` (name used by both the harness prompt and the direct mission). A duplicate file would drift; the mapping is recorded here instead. |
| D-003 | **Proposal entity.** `03_DOMAIN_DATA_API` lists entities but omits Proposal; the WebMCP spec and the approval workflow require it (mission names it "ApprovalPlan / Proposal"). | Added `proposals` table: `id, kind (meeting_create\|meeting_update\|agenda\|followup\|outcome), status (pending\|approved\|rejected\|superseded\|executed\|failed), payload (Zod-validated JSON), rationale, base_meeting_id, base_meeting_revision, project_id, actor fields, approved_by_user_id, approved_at, executed_at, verification (JSON), superseded_by_id, created/updated`. Proposals are domain data persisted in PostgreSQL like every other entity. |
| D-004 | **Approval gate for outcome tools.** `record_decision`, `create_action_item`, `assign_action_item` have no `prepare_*` tool, but the spec says mutations creating "a meeting, agenda, decision, action, or follow-up require a corresponding human-approved proposal where applicable". | Uniform rule: **every agent-initiated mutation is approval-gated.** These tools operate propose-or-execute: called without `proposalId` they create a pending `outcome` proposal and return a structured "waiting for approval" result; called with the `proposalId` of a human-approved proposal they execute it. Deterministic, keeps exactly the 20 documented tools, no ungated agent mutation path. |
| D-005 | **`verify_meeting_state` classification.** The spec lists it under "Mutating — approval-gated", but it performs no mutation. | Implemented as read-only (`readOnlyHint: true` annotation) because there is nothing to approve; it compares caller expectations against actual persisted state and returns a structured verification report. The "approval-gated" grouping is honored in spirit: it never changes state. |
| D-006 | **Meeting status semantics.** Statuses `draft | proposed | approved | scheduled | ...` describe meetings, while proposals have their own lifecycle. | `create_meeting` execution creates the meeting directly as `scheduled` (golden demo path). UI-direct creation starts as `draft`. `proposed`/`approved` are used when a proposal targets an existing draft meeting. Transitions are validated by an explicit map in the domain layer; terminal states cannot transition except documented reopen/cancel rules. |
| D-007 | **Approval → execution ordering.** Golden demo: "Human approves. WebMCP executes the approved operation." | Approval does **not** auto-execute. The approved proposal is executed by (a) the agent's mutating WebMCP tool, or (b) — when WebMCP is unavailable — an explicit human "Execute" action in the UI. Both call the same domain `executeProposal` service; execution writes verification results and audit events. |
| D-008 | **Timezones & availability.** Participants carry `timezone`, `workingHours`, `focusBlocks`. | Deterministic availability engine: working hours + recurring weekly focus blocks interpreted in each participant's IANA timezone via `Intl`-based offset math (no new dependency); busy time from existing meetings; candidate slots aligned to a 15-minute grid; results ordered ascending; capped result size. Focus blocks are weekly-recurring `(weekday, start, end, label)` — matches "Daniel has a focus block Tuesday afternoon". |
| D-009 | **Command bar with no embedded LLM.** Spec wants a natural-language entry point that is "not a full chat application". | Honest handoff surface: submitting text records it (audit event) and the UI displays it alongside a copyable prompt for the user's external WebMCP agent plus live WebMCP connection status. No fake NLP, no fabricated understanding; UI copy states that reasoning happens in the external agent. |
| D-010 | **Authentication.** Docs require "no signup friction" and authorization, but define no auth system. | Demo-mode session: signed cookie session identifying a seeded user (default Alex; switchable in Settings to exercise authorization rules). Zero passwords. All authorization is server-side from the session; documented as demo-mode, listed as a known limitation. |
| D-011 | **Actor channels in audit.** UI and WebMCP share the session; audit needs `actorType` (`human | agent | system`). | The API derives the authenticated user from the session cookie only. The client sends an explicit non-authoritative `X-MeetingOps-Channel` header (`webmcp | ui`) used **solely** for audit/actor classification and the Agent Activity display — never for authorization. Server-side authorization never depends on it. |
| D-012 | **Agent Activity truthfulness.** "Never fabricate tool events." | The Agent Activity panel renders only persisted audit events (`GET /api/activity` / per-meeting) plus real proposal state ("Waiting for approval" = a pending/approved-but-unexecuted proposal exists). No synthetic timeline entries. |
| D-013 | **WebMCP availability.** Native API exists in Chrome 149+ (Origin Trial), Edge 150+, ChatGPT Desktop. | Production registration path runs only against the real `document.modelContext`. For development/testing, the app can load a **clearly-labeled** conforming polyfill of the draft API (dev flag / test harness only) so the tool layer is exercisable; the UI status badge reports `native` vs `unavailable` truthfully. Native verification is a separate gate (TEST-10/WM-12) recorded with real client evidence. |
| D-014 | **Toolset updates on state change.** The draft API has no unregister call in the type surface (registration options accept an `AbortSignal` to unregister). | Tools are registered once with an `AbortSignal` tied to app/session teardown; state-appropriateness is enforced deterministically inside handlers (`INVALID_STATE` structured errors), so a stale registered tool can never cause an invalid state transition. Documented as the safe interpretation of "state-aware exposure". |
| D-015 | **TypeScript version.** Latest `typescript` is 7.x (native rewrite) but the lint ecosystem (`typescript-eslint@8`) supports `<6.1.0`. | Pin `typescript@5.9.x` (strict mode) for toolchain correctness; revisit when typescript-eslint supports TS 7. |
| D-016 | **Zod 4 / Vite 8 / React Router 8 / ESM.** Current majors at build time differ from what the docs assumed. | Use current stable majors with their documented APIs (Zod 4 syntax, Vite 8 + `@vitejs/plugin-react@6`, React Router 8 library mode). Node ESM throughout (`"type": "module"`). |
| D-017 | **Idempotency.** "Mutation endpoints accept idempotency keys where defined." | `idempotency_records` table keyed by `(actor_user_id, idempotency_key)` storing a canonical request hash, status, and stored response. Replay of the same request returns the original response (`IDEMPOTENT_REPLAY`); same key + different payload → `IDEMPOTENCY_CONFLICT`. Applied to all mutating endpoints and mutating WebMCP tools. |
| D-018 | **Rate limiting.** Phase 9 requires "rate limiting appropriate for demo endpoints". | `@fastify/rate-limit` (in-memory) applied to mutating and auth/session routes with demo-appropriate limits; documented. |
| D-019 | **Astryx internals vs Phosphor rule.** `@astryxdesign/theme-neutral` ships Lucide icons internally. | The app uses Phosphor (`@phosphor-icons/react`) for **all interface iconography it renders**. Astryx components may use the design system's internal glyphs for structural affordances (e.g. select chevrons) as part of the documented component system; no Lucide icon is imported by product code. |
| D-020 | **Local calendar model honesty.** "The hackathon MVP may use a local calendar domain model, but it must be clearly represented as such." | No external calendar integration exists; UI copy labels availability/busy data as MeetingOps' local domain model, and `find_available_slots`/`verify_meeting_state` results never claim an external calendar event was created. |
| D-021 | **Deployment targets.** Docs: static Vite frontend (Vercel/Cloudflare Pages), Node/Fastify backend, Neon PostgreSQL; provider-neutral code. | Full reproducible runbook + scripts + Dockerfile provided. Actual cloud deployment requires account credentials not present in this environment; the deployed smoke-test gate will be marked `UNVERIFIED` (or `BLOCKED` with reason) until executed against real infrastructure, never silently claimed. |
| D-022 | **"This week" semantics.** The agent must reason over concrete dates. | `get_today_overview` returns the server-computed current date and ISO week bounds; `find_available_slots` requires explicit `dateFrom`/`dateTo`. All window math is server-side and deterministic. |
| D-023 | **Seeded demo "today".** The golden demo must always show a meaningful "this week". | Seed data anchors to the Monday of the current week at reset time (injectable clock for tests). All seeded meetings/focus blocks/blocks derive from that anchor, keeping the demo deterministic per reset while always current. |
| D-024 | **Error taxonomy.** Stable machine codes required by API + WebMCP result contracts. | Shared `ErrorCode` enum in `packages/contracts` (`VALIDATION_ERROR`, `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `CONFLICT`, `STALE_REVISION`, `STALE_PROPOSAL`, `PROPOSAL_NOT_APPROVED`, `PROPOSAL_ALREADY_EXECUTED`, `PROPOSAL_SUPERSEDED`, `INVALID_STATE`, `IDEMPOTENCY_CONFLICT`, `RATE_LIMITED`, `UNAVAILABLE`, `INTERNAL`, …). HTTP mapping table centralized; WebMCP failures use the same codes. |
| D-025 | **Proposal supersede scope.** "Changing a material constraint must invalidate the previous proposal." | Creating a new proposal for the same scope (same project for `meeting_create`; same meeting for other kinds) supersedes the prior pending/approved proposal (`superseded`, `superseded_by_id`, audit reason). Human edits to protected meeting fields (title, purpose, time, duration, participants, project) supersede affected pending/approved proposals. Non-material fields don't. |
| D-026 | **Execution verification semantics.** "Never silently continue after failed verification." | `executeProposal` runs apply + verify inside one database transaction. Verification compares persisted rows against the proposal payload. Failure → rollback, proposal marked `failed` with the error, mutation **not** persisted, structured `VERIFICATION_FAILED` error returned. Success persists the verification report on the proposal and in audit. |

| D-027 | **Astryx ships no CSS files.** `@astryxdesign/core@0.5.2` publishes no `dist/*.css`. | All Astryx component styles are compiled from source by the `astryxStylex()` Vite plugin (`@astryxdesign/build/vite`) into `/virtual:stylex.css`, injected via `transformIndexHtml` with layers `reset, astryx-base, astryx-theme, product`. `main.tsx` imports no package CSS — only `src/styles/product.css`. Product styling uses `stylex.create` + a small `sx()` helper (`src/ui/sx.ts`) that unwraps the `.root` class group. |
| D-028 | **Channel classification per call, not global.** Audit must distinguish `ui:human` from `webmcp:agent`. | `X-MeetingOps-Channel` is sent per request from the API client (`channel: 'ui' | 'webmcp'`); WebMCP executors pass `'webmcp'`. It is audit classification only (D-011) — it never changes authorization or behavior. |
| D-029 | **Polyfill test hook.** E2E and manual verification need page-reachable tool execution; the native page surface only exposes metadata. | The dev polyfill wraps `ctx.registerTool` to record tools in `window.__MEETINGOPS_POLYFILL_TOOLS__` (Map of `{name, execute}`). E2E suites drive the real executor→API path through this hook. Native Chrome registration is verified separately (D-031). |
| D-030 | **Idempotent tool registration.** StrictMode double-effects and native duplicate detection ("Duplicate tool name") race. | `registerAllTools()` is memoized per document (module-level promise) and pre-checks `getTools()` to skip already-registered names. Verified: native Chrome 153 registers 20/20 with zero duplicate errors under StrictMode. |
| D-031 | **Native verification honesty.** Chrome 153 exposes tool metadata to the page but not page-callable `execute`. | `docs/webmcp-native-verification.md` records: native registration PASS (Chrome 153.0.8010.12, `--enable-features=WebMCP`, 20/20 tools); native execution through an external agent client (ChatGPT Desktop connector) UNVERIFIED — no external client available in the build environment. Never claimed as full native interop. |
| D-032 | **Demo routes in production.** `resetToGoldenDemo` truncates and rewrites the dataset. | `/api/demo/reset` and `/api/demo/seed` are refused with `FORBIDDEN` when `NODE_ENV=production` unless the operator sets `ENABLE_DEMO_ROUTES=true` explicitly. |
| D-033 | **E2E determinism under executed proposals.** Integration tests that execute proposals change availability, breaking slot-based assertions. | Every test uses a distinct deterministic `startAt`; E2E uses the hook-driven propose flow with slots computed live and `demo/reset` between suites (golden spec resets state). |
